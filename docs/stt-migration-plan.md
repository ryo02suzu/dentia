# dentia STT 自前化／国産化 移行プラン

> 文字起こし段（`/api/transcribe`）を OpenAI Whisper API 依存から脱却し、
> 「国産STT API → 後処理補正 → 自前 fine-tuning」へコスト順・段階的に移行するための設計書。
>
> 対象読者：dentia 開発・運用チーム（個人〜数名）
> 前提コード：`server.js`（`/api/transcribe` L320-355, `/api/generate` L252-307, 用語ヒント L316）、`index.html`（録音→送信 L1219-1247）
> 最終更新：2026-06

---

## 0. 結論（先に要約）

- **いきなり自前GPU+fine-tuningはやらない。** 小規模チームには運用負荷とコストが見合わない。
- **推奨ルート：フェーズ0（後処理補正の即時導入）→ フェーズ1（国産STT API＝AmiVoice等へ乗り換え・越境停止）→ フェーズ2（後処理＋LLM正規化の強化）→ フェーズ3（データが貯まってから自前 faster-whisper / kotoba-whisper を必要時だけ fine-tuning）。**
- 各段は**前段の費用対効果が頭打ちになったら次へ**進む。go/no-go 基準は §9。
- まず**今日できること**は2つ：(1) `TRANSCRIBE_PROMPT` の用語ヒント強化＋後処理補正辞書、(2) 評価用テストセット（30〜50会話）の構築。これだけで誤変換の体感はかなり下がり、以降の意思決定の土台になる。

データ主権の論点（要配慮個人情報の越境）は**フェーズ1で解消**できる（国産STTへ切替＝米国送信を停止）。自前GPUは「精度がAPIで頭打ちになった時」の最終手段であり、コンプラのためだけに急ぐ必要はない。

## 1. 選択肢比較（A / B / C）

### 1.1 比較表

| 観点 | **A. 国産STT API**<br>(AmiVoice 等 医療系) | **B. OSS Whisper系 自前ホスティング**<br>(faster-whisper / kotoba-whisper / ReazonSpeech) + 必要時 fine-tuning | **C. ハイブリッド**<br>(自前/API STT + 後処理補正辞書 + LLM正規化) |
|---|---|---|---|
| **素の日本語精度** | 高（電話/医療会話で実績）。話し言葉に強い | 中〜高。large-v3 / kotoba-whisper-v2 は日本語良好だが歯科語は弱い | STTの素性能 + 補正で底上げ |
| **歯科ドメイン適性** | 医療辞書は内科寄り。歯科特化は弱い（カスタム語彙登録で改善可） | fine-tuning すれば最も高くできる（ただしデータ必要） | **辞書＋LLMで歯科語を実用域に寄せやすい（最良の費用対効果）** |
| **初期コスト** | ほぼ0（契約のみ） | 中（GPU環境構築・モデル選定・検証） | 低（既存STTに後処理を足すだけ） |
| **ランニングコスト** | 従量（音声分単位）。§6参照 | GPU時間。常時起動だと高い／サーバーレスGPUで圧縮可 | 後処理のLLM正規化コスト（小）＋STT費用 |
| **運用負荷** | **最小**（SLA/監視はベンダー側） | 高（モデル更新・GPU障害・コールドスタート・スケール） | 低〜中（辞書メンテ・正規化プロンプト管理） |
| **越境/コンプラ** | **国内処理を選べば越境停止＝目的達成**（契約で国内DC/委託先確認） | **完全自社内処理が可能（最強）** | STT選択に依存（国産APIなら越境停止、自前なら完全内製） |
| **レイテンシ** | 数秒（API往復）。録音停止後 許容範囲 | モデル/GPU次第。faster-whisper large-v3 で実時間の0.1〜0.3倍程度 | STT + 後処理（LLM正規化で +1〜3秒） |
| **拡張性/主権** | ベンダーロックイン。語彙登録止まり | **モデル・データを完全に握れる。将来の自由度最大** | STT層を差し替え可能な設計にすれば両取り |
| **データ蓄積** | 音声を外部委託（契約で国内・非学習を担保） | 完全自前で蓄積→改善ループを回せる | 自前STT採用時のみフル蓄積 |

### 1.2 推奨

**「C（ハイブリッド）を土台に、STT層をA（国産API）から始め、データが貯まったらB（自前fine-tuning）へ昇格させる」** を推奨する。

理由：
1. **コンプラ（越境）は A への切替で即解決**。自前GPUを待つ必要がない。
2. **歯科語の精度は、素のSTT差し替えより「後処理補正（C）」の方が費用対効果が高い**。`#46`・`EPT`・`SRP`・`Per`・材料名などは決まったパターンの誤変換が多く、辞書＋LLM正規化で安価に潰せる。
3. **自前GPU（B）は最後**。fine-tuning は「データが十分貯まり」「API＋後処理で精度が頭打ち」になって初めて投資回収できる。

> dentia の `/api/transcribe` は入出力（音声→`{text}`）が単純なので、**STTエンジンを差し替え可能なアダプタにすれば、A→B の移行はバックエンド内の差し替えだけで済む**（フロント・`/api/generate` は不変）。これが本プランの設計の核。

## 2. 推奨アーキテクチャ

### 2.1 データフロー（全フェーズ共通の骨格）

```
[ブラウザ index.html]
  MediaRecorder (webm/mp4) ──FormData "audio"──▶
        │                                         （音声はメモリのみ・永続保存しない）
        ▼
[Node/Express server.js  /api/transcribe]
  authGuard → rateLimit → dailyCap → multer(memory)
        │
        ▼
  ┌─────────────────────────────────────────────┐
  │  STT Adapter（差し替え可能な抽象）            │
  │   ├─ provider="openai"   : 現行 Whisper API   │  ← フォールバック用に残す
  │   ├─ provider="amivoice" : 国産API（フェーズ1）│
  │   └─ provider="selfhost" : faster-whisper等   │  ← フェーズ3
  └──────────────┬──────────────────────────────┘
                 │ rawText
                 ▼
  ┌─────────────────────────────────────────────┐
  │  Post-Processor（後処理補正・フェーズ0で導入）│
  │   1) 用語辞書による決定的置換（正規表現/表）   │
  │   2) （任意）LLM正規化：Claudeで歯科表記に整える│
  └──────────────┬──────────────────────────────┘
                 │ normalizedText
                 ▼
        return { text }     ← 既存と互換（フロント無改修）
        │
        ▼
[/api/generate（Claude）]  ← 変更なし。SOAP生成は維持
```

データの所在：
- **音声**：ブラウザ→サーバーのメモリ（`multer.memoryStorage`, server.js:53-56）のみ。**ディスク永続なし**は維持。
- **フェーズ1（国産API）**：音声はベンダーの国内DCへ送信（契約で「国内処理・非学習・即時破棄」を担保）。**米国送信は停止**。
- **フェーズ3（自前）**：音声は**自社管理のGPU環境から外に出さない**。

### 2.2 STT Adapter インターフェイス（実装の核）

`server.js` の `/api/transcribe` から、エンジン非依存の関数を呼ぶ形にリファクタする。

```js
// stt/index.js（新規）
// 環境変数 STT_PROVIDER で実体を切替。入出力契約: (buffer, {filename, mime}) -> { text }
async function transcribe(buffer, meta) {
  const provider = process.env.STT_PROVIDER || "openai";
  const raw = await sttEngines[provider](buffer, meta);   // ← A/B/C のSTT実体
  return await postProcess(raw, meta);                    // ← 後処理補正（§3）
}
```

→ `/api/transcribe` は `transcribe()` を呼ぶだけになり、**プロバイダ切替は環境変数1つ**。
→ 障害時フォールバック（§8.3）もこの層で実装する。

## 3. モデル選定と後処理

### 3.1 STTエンジン候補

| 候補 | 位置づけ | 長所 | 短所 | dentiaでの使いどころ |
|---|---|---|---|---|
| **AmiVoice（医療系API）** | フェーズ1の本命 | 国内処理・話し言葉に強い・カスタム単語登録・運用ゼロ | 歯科特化辞書は要自作・従量課金・ロックイン | 越境停止＋実用精度の即時確保 |
| その他国産医療STT | 比較対象 | ベンダーにより電子カルテ連携実績 | 価格/語彙登録の柔軟性に差 | 相見積りで比較 |
| **faster-whisper (large-v3)** | フェーズ3 自前の基盤 | CTranslate2で高速・省VRAM・国内/自社内処理 | 歯科語は素では弱い・GPU運用 | 自前化の土台。INT8で省コスト |
| **kotoba-whisper-v2** | 日本語強化 | 日本語WERが良好・蒸留で軽量・faster版あり | 専門語は要 fine-tuning | 自前STTの初期モデル候補 |
| **ReazonSpeech** | 日本語大規模 | 日本語特化・話し言葉データ豊富 | 歯科特化は別途 | 比較・補助候補 |
| Whisper large-v3（本家） | 参照基準 | 精度の上限の目安 | 重い・遅い | ベンチの上限線として測定 |

**自前化の初期推奨：faster-whisper で large-v3（または kotoba-whisper-v2 の faster版）を INT8 量子化**。VRAM と速度のバランスが小規模チーム向き。

### 3.2 後処理補正（フェーズ0／Cの中核・最も費用対効果が高い）

歯科の誤変換は**パターンが決まっている**ので、まず決定的な辞書置換で潰す。

**(a) 決定的置換辞書（コードで管理・LLM不要・無料・低レイテンシ）**

```
// 例：誤変換 → 正規表記
"シャープ46" | "井桁46" | "番号46"        → "#46"
"イーピーティー" | "EPT検査"             → "EPT"
"エスアールピー" | "SRP（スケーリング…)"  → "SRP"
"パー" (歯科文脈) | "ペル"               → "Per"（根尖性歯周炎）
"プロービング4ミリ"                       → "PD 4mm"
"ビーオーピー"                            → "BOP"
"ピーシーアール"                          → "PCR"
"アールシーエフ"                          → "RCF"
材料名（"シーアールインレー"→"CRインレー" 等）
```

- 歯式の左右・歯番取り違えは誤記が致命的なので、**数字＋部位の表記ゆれ**を重点的に登録。
- 辞書は CSV/JSON で外出しし、ベータ運用で増やす（§4のアノテーションから自動抽出）。

**(b) LLM正規化（任意・精度をもう一段上げたい時）**

Claude（既に契約済み）に「歯科の聞き起こしテキストを、意味を変えず歯科標準表記に正規化する」軽量プロンプトを通す。`/api/generate` とは別の安価な短い呼び出し。

- 長所：辞書に無い揺れも文脈で吸収。
- 短所：1呼び出し増（コスト/レイテンシ +1〜3秒）。**創作・改変のリスク**があるため「表記正規化のみ・新情報の追加禁止」を強く制約し、用語辞書で抑えられる範囲は辞書を優先。

### 3.3 fine-tuning の要否と手法

- **当面は不要。** 後処理（§3.2）で歯科語の大半は救える。
- **着手条件（go基準）**：人手修正済みデータが概ね **30〜50時間**貯まり、かつ「API＋後処理」で term-level 誤り率が目標に届かず頭打ち、のとき。
- **手法**：
  - Whisper系の **LoRA / PEFT** によるドメイン適応（フルfine-tuningより少データ・低コスト・低VRAM）。
  - 必要データ目安：**最低10時間で効果が見え始め、30〜50時間で安定**（ドメインの偏り次第）。歯科語が頻出する区間を厚めに。
  - 評価は§5のテストセットで before/after を必ず測る。

## 4. データパイプライン（β音声＋修正テキスト）

> 「同意済みのクローズドβ音声＋人手修正テキスト＋歯科用語集」を、改善ループの燃料にする。

### 4.1 収集（同意・最小化）

1. **同意**：β規約に「品質改善目的での音声・テキストの二次利用」を明記し、**オプトイン**で取得（`legal/terms.html`・`docs/beta-kit.md` と整合させる）。同意のない院の音声は学習に使わない。
2. **収集経路**：通常フローでは音声を破棄する設計を維持しつつ、**同意済み院のみ**「学習用にこの録音を提供する」明示ボタンで、暗号化して収集ストレージ（国内・自社管理）へ退避。デフォルトは破棄のまま。
3. **修正テキスト**：dentia 上で歯科医師が SOAP 下書きを直す際、**文字起こし原文の修正**もUIで拾えるようにする（= 教師データ＝「STT出力 vs 正解」のペアが自然に貯まる）。フィードバック保存は `supabase/feedback.sql` を流用・拡張。

### 4.2 匿名化・前処理

- **音声**：患者氏名・電話番号・住所などPIIの発話を検出し**マスク/区間削除**。施設名・医師名も同様。
- **テキスト**：固有名詞・ID をプレースホルダ化（`<患者>`, `<日付>` 等）。
- **メタ最小化**：学習用データから、誰の診療かを復元できる情報を分離（鍵管理は別系統）。
- 匿名化済みデータのみを学習プールへ。**生データと学習プールを物理/論理分離**。

### 4.3 アノテーション → データセット化

1. ペア化：`{audio_segment, stt_raw, human_corrected}`。
2. 用語タグ付け：歯式・検査値・術式略語・材料名に**タグ**を付け、term-level 評価（§5）に使う。
3. 分割：train / dev / **test（凍結）**。test は §5 のベンチに固定し、二度と学習に混ぜない。
4. バージョン管理：データセットにバージョン番号。モデルとデータの対応を記録（再現性）。

## 5. 評価計画

### 5.1 指標（WERだけでは歯科の実用性を測れない）

| 指標 | 定義 | なぜ重要か |
|---|---|---|
| **全体 WER/CER** | 単語/文字誤り率 | 全体の地力。日本語はCER併用 |
| **Term-level 誤り率** | 歯科用語（歯式・EPT・SRP・Per・PD値・材料名・術式略語）だけを抜き出した誤り率 | **dentiaの実用性を最も左右する**。全体WERが良くても専門語が崩れると無価値 |
| **歯番・左右取り違え率** | `#46`↔`#36`、右↔左 などの取り違え | **臨床的に最も危険な誤り**。単独で監視 |
| **人手修正率** | 生成SOAPに対し歯科医師が直した割合（文字数/項目数ベース） | 体感品質・現場の手間の直接指標。最終KPI |
| **数値誤り率** | PD値・C分類など数値の誤り | 検査値の取り違え防止 |

### 5.2 ベンチ用テストセットの作り方

1. β音声から**30〜50会話**（初診/再診/SPT/補綴/根管 をバランス良く）を選び、**人手で完全な正解テキスト**を作成。
2. 歯科語に**タグ**を付与（§4.3）。これで term-level/取り違え を自動採点可能に。
3. **凍結**して固定（学習に使わない）。
4. 採点スクリプト：WER/CER（jiwer等）＋ タグ抽出による term-level ＋ 歯番・左右の混同行列。

### 5.3 現行（OpenAI Whisper+用語集）との比較方法

- **同一テストセット**を、(現行Whisper) / (国産API) / (国産API+後処理) / (自前) で流して**横並び比較**。
- 各指標の差を表で提示し、**意思決定（go/no-go）の根拠**にする。
- 「人手修正率」はβ本番でも継続計測し、移行前後で比較（A/Bテスト §8.4）。

## 6. サービング／インフラとコスト

> 金額は**概算オーダー**（2026年時点の一般的レンジ）。正式値は相見積り・実測で確定する。**為替・料金改定で変動するため、必ず最新の各社料金を確認すること。**

### 6.1 フェーズ1：国産STT API（GPU運用なし）

- 構成：現行 Render + Express のまま、`STT_PROVIDER=amivoice`。GPUゼロ。
- コスト感：**音声分単位の従量**。録音停止後に1回投げるだけなので、1診療数分×件数で見積もる。
- 小規模β（数院・1日数十件）なら**月額は数千円〜数万円オーダー**に収まる想定（要見積り）。
- メリット：**運用負荷ゼロ・越境停止・即日**。

### 6.2 フェーズ3：自前 faster-whisper（GPU）

| 方式 | 形態 | コスト感 | コールドスタート | 向き |
|---|---|---|---|---|
| **サーバーレスGPU**（オンデマンド課金） | 推論時だけGPU起動（例：秒課金型サービス） | **使った分だけ。低稼働なら最安**。1時間音声の処理は実時間の0.1〜0.3倍のGPU秒×単価 | あり（数秒〜十数秒）。dentiaは録音停止後許容なので相性良い | **小規模チームの本命** |
| クラウドGPU オンデマンド | VMを必要時に起動/停止 | 起動中ずっと課金。バッチ的運用なら可 | VM起動分 | 中規模・まとめ処理 |
| クラウドGPU 常時起動 | 24/7 起動 | **高い（小規模には過剰）** | なし | 高負荷・常時利用 |

- **推奨：サーバーレスGPU**。dentia は「録音停止後に1回・数秒〜十数秒許容」なので、常時GPUは不要。コールドスタートはモデルをキャッシュ/ウォーム1台で緩和。
- **1時間音声あたりの目安**：faster-whisper large-v3 INT8 で、GPU実処理は概ね数分。サーバーレスGPU単価×数分＝**1時間音声あたり数十円オーダー**を狙える（モデル・GPU種別で変動。要実測）。
- 量子化（INT8/INT8_float16）でVRAM・コスト圧縮。バッチ・並列で単価改善。

### 6.3 スケール・冗長化・コールドスタート

- **スケール**：録音は同時多発しないので、軽い同時実行で足りる。サーバーレスGPUの自動スケールに委ねる。
- **冗長化**：STT Adapter にフォールバック（§8.3）。自前STT障害→国産API→（最終）現行Whisper、の順で切替。
- **コールドスタート**：(a) 1台をウォーム保持、(b) モデルをコンテナイメージ/ボリュームに焼き込み起動短縮、(c) `/api/transcribe` 受信時に即ウォームアップ。

## 7. セキュリティ／コンプラ（3省2ガイドライン志向）

| 項目 | 方針 |
|---|---|
| **国内処理** | フェーズ1：国産API（国内DC・委託先を契約で確認）。フェーズ3：自社管理GPUで**音声を外に出さない** |
| **越境停止** | OpenAI（米国）送信を停止＝目的達成。フォールバックで現行Whisperを残す場合は「越境が起きうる」ことを規約・運用で明示し、同意範囲内に限定（または国産フォールバックのみにする） |
| **暗号化** | 通信TLS、保存（学習プール）は保存時暗号化。鍵はアプリと分離管理 |
| **最小保持・破棄** | 通常フローは現行どおりメモリのみ・処理後破棄（server.js:11-12, 52）。学習用退避は**同意済み・暗号化・保持期限・自動削除**を定義 |
| **アクセス制御** | 学習プール/GPU環境は最小権限・監査ログ。Supabase RLS（既存）を踏襲 |
| **ログ** | 音声・本文をログに残さない（現行は `text` をログ出力していない＝維持）。エラーログにPIIを混ぜない |
| **委託先管理** | 国産API利用は「外部委託」。委託契約・安全管理措置・再委託の確認（3省2ガイドラインの委託要件） |
| **整合** | 3省2ガイドライン（医療情報の外部保存/委託）・ISMS の観点でデータフロー図（§2.1）と保持/破棄ポリシーを文書化。`legal/` と `docs/specification.md` に反映 |

> 注：本書はコンプラの方針整理であり、法的助言ではない。正式な適合判断は専門家レビューを受けること。

## 8. 既存システムへの統合手順

### 8.1 `/api/transcribe` の差し替え（互換維持）

**変えないもの**：エンドポイントのパス・認証/レート/日次上限ミドルウェア（server.js:320 の `authGuard, rateLimit, dailyCap, upload.single("audio")`）・レスポンス `{text}`・25MB上限・フロント（index.html:1219-1247）。

**変えるもの**：本体の `openai.audio.transcriptions.create(...)` を **STT Adapter 呼び出し**に置換。

```js
// server.js（イメージ）
const { transcribe } = require("./stt");           // ← 新規アダプタ

app.post("/api/transcribe", authGuard, rateLimit, dailyCap, upload.single("audio"), async (req, res) => {
  if (!req.file?.buffer?.length) return res.status(400).json({ error: "音声データがありません。" });
  try {
    const { text } = await transcribe(req.file.buffer, {
      filename: req.file.originalname || "audio.webm",
      mime: req.file.mimetype,
    });
    return res.json({ text: text || "" });
  } catch (err) {
    console.error("[transcribe] error:", err);
    return res.status(err.status || 500).json({ error: err.userMessage || "文字起こし中にエラーが発生しました。" });
  }
});
```

環境変数（`.env.example` に追記）：

```
# STT プロバイダ切替: openai | amivoice | selfhost
STT_PROVIDER=openai
# 国産STT（フェーズ1）
AMIVOICE_API_KEY=
AMIVOICE_ENDPOINT=
# 自前STT（フェーズ3）
SELFHOST_STT_URL=
# 後処理: 辞書置換は常時ON / LLM正規化のON-OFF
STT_POSTPROCESS_LLM=off
# フォールバック順（カンマ区切り）
STT_FALLBACK=amivoice,openai
```

### 8.2 入力フォーマット互換

- フロントは `webm`（多くは Opus）／iOSでは `mp4` を送る（index.html:1222-1223）。
- 国産API・自前STTが webm/opus を直接受けない場合、サーバー側で **ffmpeg により wav/16kHz mono へ変換**してから渡す（メモリ上で完結、ディスク残さない）。Adapter 内に変換段を持たせる。

### 8.3 フォールバック（自前STT障害時に従来APIへ）

- Adapter は `STT_FALLBACK` の順に試行。primaryが例外/タイムアウト/空文字なら次へ。
- フォールバックで**越境（OpenAI）に落ちる場合は同意範囲を確認**。コンプラ厳格運用では「国産API→国産予備」のみにし、OpenAIは含めない設定も可能に。
- 全滅時は現行同様のエラーメッセージを返し、フロントは手入力にフォールバック（index.html は既に手入力欄へ結果を出す設計 L1240-1241）。

### 8.4 段階移行（A/Bテスト）

- ユーザー（院）単位で `STT_PROVIDER` を割り当て（Supabaseにフラグ）。
- 同一期間に「現行Whisper群」vs「国産API群」で**人手修正率**（§5.1）を比較。
- 有意に改善 or 同等＋越境停止メリットが確認できたら全面切替。

## 9. 段階的ロードマップと go/no-go 基準

```
フェーズ0：後処理補正＋評価基盤（今すぐ・1〜2週）
  ・TRANSCRIBE_PROMPT 強化（server.js:316）
  ・決定的置換辞書（§3.2a）導入
  ・テストセット30〜50会話 構築（§5.2）
  go→1 : 「term-level 誤り率」と「人手修正率」が計測でき、辞書で歯科語誤りが体感減少

フェーズ1：国産STT API へ乗り換え（越境停止）
  ・STT Adapter 実装、STT_PROVIDER=amivoice、ffmpeg変換、フォールバック
  ・A/Bテストで現行Whisperと比較
  go→2 : 国産APIが「現行Whisper同等以上の精度 かつ 越境停止」を満たす
  no-go : 国産APIが歯科語で明確に劣る → 後処理(C)強化で底上げ、or 別ベンダー比較

フェーズ2：後処理＋LLM正規化の強化（C）
  ・辞書を運用で拡充、必要なら STT_POSTPROCESS_LLM=on（表記正規化のみ）
  ・データ収集パイプライン（§4）稼働、修正ペアを蓄積
  go→3 : 「API＋後処理」でも term-level 誤り率が目標未達で頭打ち、かつ
          人手修正済みデータが 30〜50時間 蓄積

フェーズ3：自前STT（faster-whisper）＋必要なら fine-tuning（B）
  ・サーバーレスGPUで faster-whisper を立て、SELFHOST へ切替
  ・LoRAでドメイン適応、テストセットで before/after 検証
  go(全面化) : 自前が「国産API＋後処理」を term-level/取り違えで上回り、
               1時間音声あたりコストが許容内、運用が回る
  no-go : 精度向上が運用コストに見合わない → フェーズ2構成を継続（撤退も正解）
```

**定量しきい値の例**（β実測で調整）：
- 用語修正率（term-level 人手修正）が **目標◯%以下**になったら、その構成を採用。
- 学習データが **30時間**を超えたら fine-tuning 検証に着手。
- 歯番・左右取り違え率が **◯%以上**残るなら、後処理の取り違えルールを最優先で強化。

## 10. リスクと対策

| リスク | 兆候 | 対策 |
|---|---|---|
| **精度が出ない**（特に歯科語） | term-level 誤り率が下がらない | まず後処理辞書（安価）で潰す。LLM正規化を限定投入。自前化は最後 |
| **歯番・左右取り違え**（臨床的に危険） | 取り違え率が残る | 専用ルール＋数値/部位の表記検証。SOAPは「下書き・要医師確認」を明示（既に server.js:220-221 で担保） |
| **コスト超過** | GPU常時起動・LLM正規化乱用 | サーバーレスGPU・従量・INT8量子化・LLM正規化は辞書で足りない時だけ |
| **運用負荷** | GPU障害・コールドスタート対応に忙殺 | フェーズ1（API）で長く粘る。自前化は本当に必要になってから。フォールバックで可用性確保 |
| **データ不足**（fine-tuning できない） | 修正ペアが貯まらない | フェーズ0から収集パイプラインを先に作る。同意UI・修正UIを早期実装。貯まるまで自前化しない |
| **越境の取りこぼし** | フォールバックでOpenAIに落ちる | コンプラ厳格運用は国産フォールバックのみ。越境経路は規約・同意で明示 |
| **LLM正規化の改変** | 正規化が内容を創作 | 「表記正規化のみ・新情報追加禁止」を強制。辞書優先。差分を監査 |
| **ベンダーロックイン**（国産API） | 価格改定・仕様変更 | STT Adapter で抽象化済み＝差し替え可能。自前STTへの退路を常に確保 |
